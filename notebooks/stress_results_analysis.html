Supplementary Stress Evaluation — L1 vs S1 near capacity¶

This notebook is supplementary to, and does not replace or reinterpret, the primary 18-run formal experiment analyzed in formal_results_analysis.ipynb. That experiment found that at a fixed 50 QPS neither architecture shows meaningful p95 degradation under concurrent indexing (D_p95 mostly 0.7-1.0) — plausibly because 50 QPS never puts either system under real load pressure (p95 latencies were only ~5-8ms, CPU stayed low in both architectures).

This experiment instead pushes each architecture toward its own approximate capacity ceiling before comparing query-only vs. query+write behavior, to test whether the same "no measurable degradation" finding still holds under load pressure, or whether it was an artifact of running far below capacity.

Method¶

  1. Capacity-staircase probe (scripts/stress/find_capacity.py): a query-only doubling staircase (50, 100, 200, ... QPS) run separately against each architecture to find its approximate sustainable-QPS ceiling, using a predeclared knee-detection rule (rate collapse below 95% of offered QPS, a p95 latency jump >3x between adjacent rungs, or error rate above 1.0%). Results: max_sustainable_qps = 1500 (L1), 1600 (S1).
  2. Frozen stress QPS: QPS_stress = round(0.75 * min(1500, 1600) / 10) * 10 = **1120** — a common load level both architectures can sustain, applied identically to both so the comparison stays apples-to-apples.
  3. Two new conditions per architecture, 3 repetitions each (12 runs total), each with an 8-minute (480s) measurement window preceded by a 30s discarded lead-in and a 180s warm-up:
    • Stress-W0: 1120 QPS query-only (no writes).
    • Stress-W2: 1120 QPS query + 500 docs/s concurrent indexing.
  4. Metric: same convention as the primary experiment — D_p95_stress = p95(Stress-W2) / p95(Stress-W0), computed per architecture, per repetition.

No artificial workload-distorting tricks (forced merges, refresh=true, tiny heaps, slow disks, RAM starvation) were used — same corpus, same query set, same Docker resource limits as the primary experiment (experiment-config.json, untouched).

Deferred: an "L1-R" replica-only-routing control was considered and explicitly deferred (not implemented) — OpenSearch has no supported preference=_replica mechanism and L1 has no allocation-awareness config to safely pin shard placement.

All 12 stress runs are valid (see results/stress/<system>/<workload>/r<n>/validity.json).

def _load_json(path: Path) -> dict | None:
    if not path.exists():
        return None
    with open(path) as f:
        return json.load(f)


def _container_totals(container_summary: dict | None) -> dict:
    if not container_summary:
        return {"cpu_pct_avg_total": np.nan, "cpu_pct_max_total": np.nan, "mem_mb_avg_total": np.nan, "mem_mb_max_total": np.nan}
    return {
        "cpu_pct_avg_total": sum(c["cpu_pct_avg"] for c in container_summary.values()),
        "cpu_pct_max_total": max(c["cpu_pct_max"] for c in container_summary.values()),
        "mem_mb_avg_total": sum(c["mem_mb_avg"] for c in container_summary.values()),
        "mem_mb_max_total": max(c["mem_mb_max"] for c in container_summary.values()),
    }

Reusable dot + median + min-max plot helper¶

Same presentation convention as the primary notebook: every one of the 3 repetitions is plotted as its own point, with a median marker and a min-max range bar, rather than collapsing to mean +/- std (n=3 is too small for std to be a stable/trustworthy summary).

def plot_dot_median(ax, df, metric, title=None, ylabel=None, ref_line=None,
                    systems=("L1", "S1"), workloads=WORKLOADS_UPPER, jitter=0.04):
    x = np.arange(len(workloads))
    n = len(systems)
    span = 0.3
    offsets = {s: (i - (n - 1) / 2) * (span / max(n - 1, 1)) for i, s in enumerate(systems)}

    for system in systems:
        for i, wl in enumerate(workloads):
            vals = df[(df["system"] == system) & (df["workload"] == wl)][metric].dropna().to_numpy()
            if len(vals) == 0:
                continue
            xs = x[i] + offsets[system] + RNG.uniform(-jitter, jitter, size=len(vals))
            ax.scatter(xs, vals, color=SYSTEM_COLOR[system], alpha=0.85, zorder=3, s=45,
                       label=system if i == 0 else None)
            med = np.median(vals)
            ax.plot([x[i] + offsets[system] - 0.09, x[i] + offsets[system] + 0.09], [med, med],
                    color=SYSTEM_COLOR[system], linewidth=2.8, zorder=4)
            if len(vals) > 1:
                ax.vlines(x[i] + offsets[system], vals.min(), vals.max(),
                          color=SYSTEM_COLOR[system], alpha=0.35, linewidth=1.5, zorder=2)

    if ref_line is not None:
        ax.axhline(ref_line, color="gray", linestyle="--", linewidth=1, zorder=1)
    ax.set_xticks(x)
    ax.set_xticklabels(workloads)
    if title:
        ax.set_title(title)
    if ylabel:
        ax.set_ylabel(ylabel)
    ax.legend()

Diagnostic 4: within-run latency drift over the 480s measurement window¶

Buckets each run's queries into 10s windows and plots bucket-p95 over time — reveals whether an aggregate p95 is hiding a warm-up tail, a spike, or slow drift within the longer 480s window used here (vs. 300s in the primary experiment).

BUCKET_S = 10


def load_measurement_queries(system_dir: str, workload_dir: str, rep: int) -> pd.DataFrame:
    path = RESULTS_ROOT / system_dir / workload_dir / f"r{rep}" / "queries.csv"
    df = pd.read_csv(path)
    lead_in = LEAD_IN_S[workload_dir]
    df = df[df["tick_offset_s"] >= lead_in].copy()
    df["time_s"] = df["tick_offset_s"] - lead_in
    return df


def bucket_p95(df: pd.DataFrame, bucket_s: float = BUCKET_S, measurement_s: float = MEASUREMENT_S) -> pd.Series:
    bins = np.arange(0, measurement_s + bucket_s, bucket_s)
    labels = bins[:-1] + bucket_s / 2
    df = df.copy()
    df["bucket_mid"] = pd.cut(df["time_s"], bins=bins, right=False, labels=labels)
    return df.groupby("bucket_mid", observed=True)["latency_ms"].quantile(0.95)
